# Phase 8 — practical diagnostic build strategy

2026-10-22. **Recommendation: a fresh credential-free Windows VM with every virtual NIC disabled/removed and host integration disabled, on separately approved sufficient storage. NO-GO on current verified resources.** This is simpler to verify than developing a host-wide event-security controller, but no ready isolated guest has been demonstrated. No build is authorized.

Investigation was read-only except this document. No VM/toolchain/build/ADB/emulator/installer was launched; no network probe, firewall/permission/environment/partition change, copy, cleanup or dependency download occurred. Metadata of existing tools/VM registrations was inspected; guest disks, memory images and credentials were not opened or imported.

## A — installed offline Windows build on the host

**Advantage:** no guest OS/toolchain duplication; existing QA Gradle outputs already select `C:\Users\Abood\AppData\Local\StudyBirds\qa-diagnostic-phase8\gradle-build`. Source-local Flutter compilation cache still uses D. The proposed 16 GiB C / 6 GiB D start thresholds fit storage, but the lower D threshold has not been approved and RAM currently does not fit conservative execution headroom.

**Missing boundary:** an ordinary process running as Abood can access production repositories, signing files, profile credentials and host network. C output placement, exact tasks, hashes, an empty TCP snapshot, new working directory and `--offline` do not remove those capabilities. Gradle configuration, plugins, Flutter/Dart analytics and child programs execute host code during compilation; API startup being disabled in Dart does not constrain them.

A restricted token/AppContainer can provide resource/network isolation in principle ([Microsoft AppContainer](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)), but there is no installed, verified Java/Gradle/Flutter containment launcher here. Establishing it would require scoped filesystem permissions/capabilities, all child processes contained, native-tool/loopback compatibility and real failure tests. This is more work than the current preparation model and would need explicit approval. A normal local account alone, disabling a proxy or an offline Gradle flag is insufficient. Physically disconnecting all host uplinks is possible in principle but disrupts the host and still does not protect readable host credentials or later exfiltration; not recommended as the sole boundary.

**Verdict A: NO-GO as currently implemented.** Monitoring can detect some mistakes; it is not an enforceable network/credential boundary. No global firewall change is proposed, and no per-process deny mechanism has been verified.

## B — disposable VM / isolated builder

Use a clean Windows guest compatible with the existing Windows toolchain, not an unverified personal VM or a Linux guest that would need different native SDK/JDK binaries. Allocate a planning **4 vCPU / 8 GiB RAM**. Require at least **10 GiB host available RAM before boot**, then monitor actual guest/host pressure. These are planning limits, not measured performance guarantees. The current 4-core/16 GiB host can potentially accommodate one build guest after other applications close; it cannot be claimed ready with 1.6–2.1 GiB available.

For storage, provision an owner-approved location with **at least 120 GiB free** as a conservative full Windows guest + offline tools + scratch budget, or first produce a measured smaller manifest-based budget with >=16 GiB guest build headroom and >=8 GiB host-volume reserve. This is a planning reserve, not a claim that a minimal guest needs 120 GiB. No such location was verified. Existing C free space is not sufficient for an unplanned full-toolchain clone. An external SSD or already provisioned separate builder is preferable to deleting protected material; connecting/provisioning it requires approval.

**Network deny without global firewall changes:** configure the new VM itself with **all virtual adapters disabled/removed**, no NAT, bridge, host-only/internal network or generic tunnel; disable USB networking passthrough and shared clipboard/drag-and-drop, shared folders, guest-control file exchange, serial/parallel network redirection and other host channels. Use explicit offline import media and a guest-private writable disk. Do not expose host repositories, profiles, credentials or dependency caches as writable shares. Oracle documents the per-adapter modes and their host/external reachability; host-only is not equivalent to no host access ([VirtualBox networking](https://docs.oracle.com/en/virtualization/virtualbox/7.2/user/networkingdetails.html)).

This boundary is verifiable by reviewing the powered-off VM configuration and, after separate boot approval, checking effective VM devices plus guest adapters/routes without contacting external or production endpoints. No-NIC absence can establish no normal guest network path without implementing complete per-packet host attribution. It does not prove zero attempted telemetry or protect against hypervisor vulnerabilities; no absolute containment claim is appropriate. Build plugins could still write telemetry locally, so never reconnect the disposable guest later or import its whole user profile back to the host.

**Verdict B:** preferable security design and simpler verification, **not ready now**. VirtualBox presence is useful, but VM provenance, OS/toolchain, storage, RAM and effective isolation are unresolved.

## Build-time versus Android-runtime boundaries

During **build**, protect the host from build scripts/tool subprocesses: no credentials, no host source/output write access, no external egress, bounded storage/process lifetime, exact reviewed inputs and APK destination. The local QA API, database, email, TLS service, OCR camera, OneSignal/provider runtime and Android emulator are not required just to compile a diagnostic APK.

During **Android runtime**, separately validate provider boot, local CCT routing, ML Kit/OCR, DNS/HTTP attempts, SQLite/deferred jobs, TLS hostname checks and local QA service/account isolation. A networkless builder says nothing about what the APK will do when installed. Keep `QA_RESOURCES_VERIFIED=false`, CA empty and the QA manifest/provider exclusions/local backend unchanged. No APK installation or runtime success is implied.

## Practical approved-later sequence and measurable acceptance

1. **Approve isolated preparation only:** identify a clean licensed Windows image/builder, exact new storage location and resources. Do not modify/import/resume the personal VM. Owner frees memory manually; verify resource thresholds and no original file/link/index changes.
2. Export a **sanitized, hash-manifested copy** of the needed app source and exact offline tools into a new staging location; retain all original repositories and `.git` relationships untouched. Exclude original keystores, `key.properties`, production `.env`, provider credentials, browser profiles, QA databases/storage/TLS private material and original APKs. Source files themselves require a secret scan before export. Do not copy all of `.gradle` (user properties/init scripts may carry authority); select dependency/wrapper artifacts and Pub packages without credentials or live shared owners. Missing offline packages mean stop; no network enablement or upgrade.
3. Use guest-only paths/profile for project state, TEMP, dependency copies and outputs. Absolute host source/package-config references must be regenerated/reviewed **in the copy**, never in host repositories. Guest paths may require a separately approved QA-only storage adjustment in the copy. A fresh guest-only debug key, if required, needs explicit approval; never use production signing material. Preserve production branch/settings and no release task.
4. Before boot/build, attest **zero enabled VM NICs and zero host integration channels**, sanitized input manifest, no mounted host source/credential disk, disk/RAM headroom and fixed copied QA source/config. No global host network/firewall change. If a boundary cannot be verified, stop.
5. Only after another explicit owner decision, review a minimal **copy-local** QA gate change for the exact Stage A roots and separately approved Stage B root from the controlling review. Keep the host gate unchanged. The VM boundary removes the need for a bespoke host packet/process/path security framework; it does not remove exact task, source/hash and stage-evidence checks.
6. Acceptance for a single attempt: offline resolution succeeds without network devices or downloads; Stage A exits 0; new guest merged XML passes strict provider/local-transport checks; B separately authorized then exits 0; artifact is `com.studybirds.app.qa`, qaDebug/x86_64, expected new APK name/hash, pending resources=false. Record capacities, configuration and logs. No native-runtime/OCR claim. Unknown graph/tasks/output/config, missing packages or isolation drift => stop and no retry without review.
7. Power off the guest, then use a separately approved narrow offline export of **only** the new APK, hashes and diagnostic text into a new quarantine/output location. No writable host share during build; no executable export auto-run. Do not attach guest storage to a live host account with autorun or import its profiles. Verify the host's protected 139 hashes, original APK and Git HEAD/index/worktree registrations remain unchanged.

Rollback: leave host repositories/gate untouched, stop only the approved disposable VM by owner-authorized means, and preserve guest outputs for review. Do not delete guest disks, original VMs or staging data automatically. A failed attempt consumes its approval. Host restoration/reset/stash, shared-cache cleanup and reconnection are not rollback steps.

## Reuse versus unnecessary complexity

Reuse controller core's exact roots/config/hash comparisons, default denial, capacity sampler rules, negative cases, separate A/B evidence and single-attempt/disarm concept. Existing receipt tests are simulations, not authenticated authority. Keep trusted owner confirmation and a durable run record appropriate to the selected boundary.

Do not treat modeled sensors as installed protection. In a truly networkless, host-unshared guest, exhaustive host per-PID egress attribution, live filesystem event allowlisting and a general credential-aware broker add little value for one bounded build. Prefer VM device/config attestations, private guest storage and before/after input/output hashes. Any simplification of earlier controller requirements is itself a documented owner-approved strategy change; it must not silently enable the host gate or reclassify unimplemented checks as passing.
