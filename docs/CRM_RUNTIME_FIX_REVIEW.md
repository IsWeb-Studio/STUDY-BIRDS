# إصلاح توقف CRM واستهلاك الذاكرة — مراجعة الدمج

الحالة: تعديلات محلية فقط. لم يُنشر الخادم، ولم يُتصل بقواعد الإنتاج أو يُحذف أي سجل منها.

## مكتمل في المسارات الحالية

- طابور الحفظ يستخدم Immer لنسخ الأجزاء المتغيرة بدل `structuredClone` لحالة CRM كاملة.
- يبقى الحفظ متسلسلًا، ولا تصل التعديلات المرفوضة إلى الكاش المحفوظ. العمليات التي لم تغيّر بيانات لا تعيد الكتابة.
- النسخ المطلوبة صراحةً للأرشيف ما زالت كاملة؛ لا يحذف الإصلاح أرشيف الدليل أو تاريخ الرسائل.
- كاش نماذج القراءة يحتفظ بمراجع البيانات بدل نسخة JSON نصية إضافية لكل مجموعة. كاش مقارنة الدليل يحتفظ ببصمة SHA-256 بدل النص الكامل.
- إعداد شركة المزامنة الخاطئ ينتج تشخيصًا واضحًا، ويظهر معرّف الشركة الحالية داخل شاشة إعدادات الربط للحساب المخوّل. لم يُستبدل معرّف شركة تلقائيًا ولم تُنقل بيانات بين الشركات.
- المحاولات الدورية الفاشلة تتباعد حتى 15 دقيقة، ولا تتداخل؛ تصحيح الإعداد يعيد الفاصل الطبيعي عند المحاولة الناجحة.

## مدمج ومختبر محليًا في الخادم الأساسي

ملفات CRM:

- `server/src/integrations/meta/durableWebhookInbox.js`
- `server/src/integrations/meta/metaWebhookRuntime.js`
- `server/src/integrations/meta/metaWebhookProcessor.js`
- `server/src/startupReadiness.js`

الدمج يستبدل معالج POST الخاص بـMeta بوحدة التشغيل، ويشغّل استعادة المعلّق بعد اكتمال التهيئة. يحفظ الاستلام في مجموعة إضافية `meta_webhook_inbox` قبل الرد 200؛ فشل الحفظ يرجع 503 حتى يعيد المزود المحاولة. لا توجد TTL أو عملية تنظيف للسجلات. الأحداث القديمة تبقى في `webhookEvents` ويُحدّث وضع معالجتها بعد النجاح.

العامل يأخذ lease مشتركة ويجددها، ويعالج دفعة محدودة. يبقى payload محفوظًا عند الفشل وإعادة التشغيل؛ إعادة المحاولة لا تعيد إنشاء الرسالة ذات معرّف المزود نفسه. المعالج الجديد يتعامل مع جميع رسائل دفعة WhatsApp بدل أول رسالة فقط.

وحدة الجاهزية تفتح المنفذ على `0.0.0.0` قبل انتظار تهيئة قاعدة البيانات والدليل. `/api/health` يرجع 503 أثناء التهيئة و200 عند الجاهزية. بقية الطلبات ترجع 503 و`Retry-After` أثناء التهيئة، بحيث لا يُؤكد استلام رسالة قبل حفظها.

تم توصيل الوحدات بـ`server/src/index.js` بعد موافقة المستخدم. لم يُنشر التغيير ولم تُستخدم قواعد الإنتاج في الاختبار. عند فشل الاتصال أثناء استعادة التاريخ القديم يُعاد المحاولة تلقائيًا، وتبقى الأحداث محفوظة. بعد توقف مفاجئ قد تنتظر الاستعادة انتهاء lease القصيرة (نحو دقيقتين)، ولا تُحذف البيانات خلالها.

## نتائج الاختبار وحدودها

- اختبار بسقف heap قدره 256MB احتفظ بـ90 ألف سجل وهمي، ونفّذ 100 تعديل صغير. heap بعد التنظيف بقي نحو100MB قبل التعديلات وبعدها.
- اختبار HTTP مع MongoDB replica set محلية أكد عدم انتظار الاستلام لطابور CRM المحجوز، ومنع تكرار الحدث، وحفظ الأحداث الفاشلة واستعادتها بعد إعادة التشغيل مع الاحتفاظ بالتاريخ القديم.
- اختبار HTTP مستقل أكد سلوك الجاهزية ورفض قبول العمل قبلها.
- اختبار عملية الخادم كاملة بسقف256MB نجح: فتح المنفذ أثناء انتظار API وهمي محلي، 503 قبل الجاهزية، حفظ دفعة الرسائل مرة واحدة، الاحتفاظ بالطلاب والفواتير والرسائل القديمة، استعادة المعلق بعد إعادة التشغيل، ومنع تراجع حالة الرسالة المقروءة بسبب إشعار قديم.
- نجح الفحص النهائي:117 اختبارًا للربط والوحدات، بالإضافة لاختبارات MongoDB المعزولة للخادم والاستقبال.
- هذه ليست قياسات أداء للإنتاج، ولا تثبت انتهاء كل أسباب نفاد الذاكرة في خدمة Render. لا يزال app_state يُكتب كاملًا عند التغييرات الفعلية؛ تحويل التخزين الأساسي إلى معاملات ومجموعات منفصلة عمل مستقل لم يُنفّذ هنا.

## قبل النشر

1. نسخ احتياطي كامل ومتحقق منه وتجربة استعادة في بيئة معزولة، وفق طلب الحفاظ على البيانات.
2. تعيين `STUDY_BIRDS_COMPANY_ID` على Render إلى معرّف الشركة الصحيح من إعدادات الربط المصادق عليها. لا يمكن تصحيح قيمة Render من الملفات المحلية وحدها.
3. تثبيت الاعتماد الجديد من `server/package-lock.json` عند البناء.
4. نشر إصلاح الذاكرة وتشخيص الإعداد ثم قياس heap وRSS وزمن Webhook وطول طابور المعالجة.
5. انشر الإصدار المدمج بعد النسخ الاحتياطي وضبط health check إلى `/api/health`. اختبارات الخادم الكامل والتوقف والاستعادة أُجريت محليًا؛ تبقى مراقبة الإنتاج بعد النشر مطلوبة.
6. لا ترفع حد Node heap عشوائيًا دون معرفة ذاكرة خطة Render؛ الذاكرة الكلية تشمل أجزاء خارج heap.
